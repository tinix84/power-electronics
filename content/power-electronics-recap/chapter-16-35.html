16.35 The firmware calculates the same gain: why does one PWM period make the loop unstable?

Riddle: a proportional controller stabilizes a first-order plant. The controller is implemented digitally without changing its gain, but a new PWM command takes effect one update later. Why can a plant with just one stable pole now oscillate with growing amplitude?

The controller acts on an old measurement. Reading the formula correctly is not sufficient if the timing differs from the design. TI's digital-control timing discussion describes how dedicated PWM register-load events can delay a computed update and reduce phase margin. The CPU's execution time alone is not the full sample-to-actuation latency.

Separate the command hold from the update latency

Use a single sampling/update rate fs = 1/Ts, synchronized with the PWM period in this example. The numerical model holds the average actuator command constant during each period; it does not simulate individual switching edges. Distinguish these schedules:

At time k Ts:       acquire y[k]

Ideal reference:   apply u[k] = -K y[k] throughout [k Ts, (k+1) Ts)
Delayed schedule:  apply u[k] = -K y[k-1] throughout [k Ts, (k+1) Ts)
                   the new result -K y[k] waits until (k+1) Ts

The first schedule is an ideal zero-latency reference, not a claim of instantaneous ADC/CPU hardware. The second has one complete period of additional command latency. Faster code may not shorten it unless the command meets an earlier register-load deadline. Actual carrier type, sampling phase and update policy determine the effective modulator timing; imperix's delay-identification note distinguishes sensing, sample-to-update and modulation delays.

Below the first hold zero, the sine ratio is positive and the hold phase is −ωTs/2. Well below the update rate its magnitude is close to one, motivating the half-period delay approximation. One extra period contributes exp(−sTs), giving an approximate hold-plus-update budget of 1.5Ts. This is the budget for the stated schedule; it is not a universal PWM delay.

Additional ADC, filtering and sensor delays would need their own defined contributions. Do not count the same hold twice when using an exact discrete plant.

Exact results: same plant, same gain, different timing

At fs = 20 kHz, Ts = 50 µs, a = 0.606531 and b = 0.393469. Compare four configurations:

Controller and schedule Exact gain crossover Exact phase margin Largest pole magnitude Verdict
K = 3, 20 kHz, ideal immediate update 5066.87 Hz +57.88° 0.57388 Stable
K = 3, 20 kHz, one-period delay 5066.87 Hz −33.32° 1.08647 Unstable
K = 2, 20 kHz, one-period delay 2882.98 Hz +38.88° 0.88710 Stable
K = 3, 40 kHz, one-period delay 4613.61 Hz +45.88° 0.81462 Stable

The first two cases have exactly the same discrete crossover and magnitude curve. The added 50 µs latency costs 91.20° at their 5066.87 Hz crossover, changing +57.88° into −33.32°. The immediate-update pole is −0.57388, which lies inside the unit circle. The delayed poles are 0.303265 ± j1.043282, with magnitude 1.08647: the oscillatory sampled response grows. This is a timing-induced instability, independently established by the pole locations.

For the first-order plant and this proportional controller, the immediate-update stability range is 0 < K < (1 + a)/b. The one-period-delay range narrows to 0 < K < 1/b. At 20 kHz these upper bounds are approximately 4.083 and 2.5415 respectively. K = 3 lies between them. These bounds belong to this model; they are not universal controller-gain rules.

Why a phase-budget estimate is useful, but not the final proof

At the old continuous crossover of 4501.58 Hz, a half-period hold at 20 kHz would cost about 40.51°, and the extra period another 81.03°. Subtracting those from the continuous margin warns of a serious problem. It is not the exact digital margin: the crossover and the sampled frequency response must also be recalculated.

Here crossover is roughly a quarter of the 20 kHz update rate, so a simple low-frequency delay approximation is not quantitatively reliable. The table uses the exact discrete loop, not that subtraction.

The plotted free responses start with y[0] = 0.01 and, for the delayed cases, y[−1] = 0.01. A small perturbation decays in the stable cases and grows in the delayed K = 3 / 20 kHz case. Between samples, the continuous plant is integrated with the applied command held constant, so the simulation checks both the sampled recurrence and the intersample trajectory.

Change one thing: keep the hardware rate and lower K to move crossover down; or keep K and shorten the period. Both remedies work in the stated example, with different performance and implementation costs. A higher sampling rate alone is not a remedy if the PWM command is still updated at the old rate; the model must use the actual actuation schedule.

Avoiding an extra missed update can be as valuable as reducing arithmetic time. Predictive control is another possible design approach, but needs a validated model rather than treating the delay as absent.

This is an exact linear analysis of the specified sampled first-order plant with a held average PWM command. It excludes carrier ripple, nonlinear duty limits, sensor filters, quantization and jitter; the ideal no-latency case is a reference bound. The growing linear response is not a prediction that hardware amplitudes grow without saturation.

Continuous-time Nyquist intuition still applies through the correct discrete contour, but the definitive test here is the complete augmented-state pole set inside |z| = 1.

Two valid remedies. With 20 kHz hardware fixed, choose K = 2 as the demonstrated stable remedy. Its lower crossover costs response speed. If the faster response is required, investigate the 40 kHz update with K = 3, accepting tighter timing demands.

Both pass this model's pole test. A faster ADC alone is not the second remedy: the command must actually reach the PWM at the higher update rate.
